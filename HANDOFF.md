## Standing rules (always in force)
- Build things completely and correctly. Flag genuinely ambiguous requests instead of guessing — ask via AskUserQuestion before starting large/ambiguous features, not after.
- Fix small/quick issues immediately instead of deferring them.
- Before every commit/push: `npx tsc -b` (clean), `npx vite build` (clean), and check CSS brace balance if `styles.css` was touched.
- No local dev environment exists for the user — everything happens in this sandbox. Git push needs a credential helper pointed at the PAT stored in `.git-credentials-ergon` in the project root:
  `git config credential.helper "store --file='$(pwd)/.git-credentials-ergon'"` (must single-quote the path — it contains a space).
- **Any new migration that creates a table meant to be re-acquired/reused by key (locks, dedupe-by-key patterns, etc.) must use an atomic upsert-reclaim RPC, not a plain `INSERT`.** See "Transaction lock gotcha" below — this exact mistake caused every second-ever save on a given key to silently fail for an unknown length of time.
- Any function/handler that creates a new row a user will look back on later (inventory movements, audit-style records) should stamp who did it (`authSession.email`) at creation time. See `recordMovements()` in `Inventory` state for the established pattern — don't add a new inventory-movement-creating call site without routing it through that helper.
- **Any raw `<table>` on a page reachable on mobile must be wrapped in a `.table-scroll` div** (`overflow-x: auto`). `html`/`body` now have `overflow-x: hidden` (2026-08-17 fix, see work log) specifically so a wide unwrapped table can't push the whole page wider than the viewport again — an unwrapped table doesn't just get its own horizontal scrollbar, it corrupts where `position: fixed` elements (the mobile bottom nav) render on that page. If you add a new data table, wrap it from the start.
- **When a feature ported from VLTD doesn't behave the same in Ergon, diff against VLTD's actual working config/code before inventing a theory.** Wasted a round-trip guessing "DevTools emulation is flaky" for the install banner not showing when the real answer (a manifest icon below Chrome's 192px minimum) was one `diff` against VLTD's `manifest.json` away. VLTD is right there on disk (`C:\Users\EK\VLTD`) -- check it first.
- **When E says "do the whole site"/"every page" and gives a standing go-ahead to keep working without checking in, do the whole thing — don't silently narrow it to a curated "high value" subset.** Converting only 3 "high-traffic" tables to mobile cards and quietly skipping ~18 admin/back-office ones (on the assumption they're desktop-only) cost E an hour: they came back expecting the full rollout done, found gaps, and had to spend time re-discovering and re-reporting what was missed instead of that hour being productive. If full bespoke treatment for every item is too slow to do in one pass, ship a lighter universal fallback for the rest in the same batch (see `.stack-table-mobile`) rather than leaving some silently undone — a complete-but-less-polished pass beats a polished-but-partial one when the user has explicitly asked for "everything" and stepped away.
- **Before declaring a CSS fix "sitewide" or "done," check whether another rule elsewhere in `styles.css` already targets the same class.** The `.metric-grid` mobile fix (tightened stat tiles, 2026-08-18) was correct in isolation but got silently overridden the whole time by a separate, pre-existing `@media (max-width: 760px)` block further down the file that also listed `.metric-grid` and forced it back to 1 column -- later rules win ties in the CSS cascade, and E had to point out the fix visibly wasn't working before this was caught. `grep -n "\.classname"` across the whole stylesheet before trusting a fix, not just the block you just wrote.
- **`.stack-table-mobile` hiding `<thead>` is only safe for self-descriptive text cells (names, emails, statuses).** A bare checkbox or a lone number means nothing once separated from its column header -- Notification Rules' channel-toggle checkboxes were completely ambiguous with the header gone (E: "wasted space... not tightening up and being readable"). Use the `data-label="<same text as the <th>>"` + `::before { content: attr(data-label) }` pattern (`styles.css`, in the `.stack-table-mobile` mobile block) on any `<td>` whose value needs the column context restored -- see Notification Rules, the Form Builder's Required checkbox, Project BOM, Site Hardware/Pre-Sales Rules, Standard Install Times, Schedule Template phases, and Catalog Price Change Requests for the pattern. When adding a new `stack-table-mobile` table, default to adding `data-label` on every non-obvious cell rather than assuming it'll be fine.
- **A Postgres column added as "a direct FK" in a comment is not actually a FK** unless the DDL has `references <table>(id)` on it. `inventory_movements.build_transaction_id` (migration 021) was silently a bare `uuid` for a long time because of exactly this — see migration 075. When adding a column meant to be embedded via PostgREST (`alias:table(cols)` select syntax), double-check the constraint actually exists, not just the comment claiming it does.

## Mobile table -> card-list rollout (in progress, 2026-08-18)
E: "the entire site should be optimized this way" (referring to the Product Catalog mobile card list) and gave a standing go-ahead to keep converting the rest of the wide desktop-style tables without checking in each time, as long as each one follows the same pattern -- just keep this doc updated per batch. **If you're picking this up mid-rollout, check the task list (TaskList tool) for the current in-progress/pending items**, then keep going with the pattern below.

**The pattern** (established on Product Catalog, `main.tsx` ~12251, and Site Builder, ~15242): below 760px, hide the existing `<table>` (wrapped in a `*-table-scroll` div, `display: none` in the same `@media (max-width: 760px)` block the table already had overrides in -- don't create a new duplicate media query, extend the existing one for that page) and show a parallel `.mobile-card-list` built from the *same* array/`.map()` the table uses, so there's no new data plumbing. Card building blocks are shared generic classes now (added 2026-08-18, `styles.css` ~5893): `.mobile-card-list` (container), `.mobile-card` (one card), `.mobile-card-row` (icon/title row), `.mobile-card-title`, `.mobile-card-meta` (small muted line), `.mobile-card-pills` (status badges), `.mobile-card-filters` (search/filter inputs pulled out of the table's `<thead>` filter row, since those were themselves only reachable via horizontal scroll -- always put filters at the top of the mobile list, not buried). Product Catalog and Site Builder predate the shared classes and use their own prefixed set (`.catalog-mobile-*`, `.site-builder-mobile-*`) -- don't bother retrofitting those, just use the shared classes for everything converted after Inventory.

**Nested-button gotcha:** if a row has real action buttons (Receive/Adjust, Delete, etc.), do NOT make the outer card a `<button>` -- HTML doesn't allow nesting interactive elements, and while React's direct-DOM rendering (not innerHTML parsing) means the browser mostly tolerates it, it's invalid markup and risky. Use `<div className="mobile-card" role="button" tabIndex={0} onClick={...} onKeyDown={(e) => (e.key === "Enter" || e.key === " ") && ...}>` instead, with real `<button>`s nested inside wrapped in a `<span onClick={(e) => e.stopPropagation()}>`. See Inventory's card (`main.tsx` ~7638) for the reference implementation. Site Builder's card (built one batch before this rule was written) does nest a delete `<button>` inside the outer `<button>` -- it works in practice but isn't the pattern to copy; worth fixing if touching that card again.

## Data model / architecture notes
- Persistence: raw `fetch()` calls against Supabase REST in `src/persistence.ts` (no Supabase JS client).
- Any new table needs `enable row level security` **plus** at least one policy, even if fully permissive (`using (true) with check (true)`) — otherwise triggers running as the calling user get blocked.
- Ref-number pattern to reuse for any future entity needing a stable sequential reference: create a `<entity>_ref_counters (year int primary key, next_seq int default 1)` table with RLS + policies, a `before insert` trigger doing `insert ... on conflict (year) do update set next_seq = next_seq + 1 returning next_seq - 1 into seq`, format as `'PREFIX-' || year || '-' || lpad(seq::text, 4, '0')`, and a backfill `do $$ ... $$` block for existing null rows.
- **Key-reuse table pattern** (locks, or anything else identified by a reusable key that gets "released"/soft-closed rather than deleted): never do a plain client-side `INSERT`. Write a `security definer` Postgres function that does `INSERT ... ON CONFLICT (key) DO UPDATE ... WHERE <row is actually free> RETURNING *`, call it via `rpc/<function_name>` from the client, and treat "no row returned" as "still locked." See migration 069 / `acquireTransactionLock` in `persistence.ts`.
- BOM lines (`BomLine` / `project_bom_lines`) have **no stable id** in the app layer — they're identified by `item` (product name) everywhere, including the new Shipping feature's line items (`item_name`, not a FK). Don't introduce a `bom_line_id` FK assuming one exists; it doesn't.
- `ProjectSite.locations` / `.shippingAddresses` / `.shipments` / `.saas*` fields are all **optional** (`?`) on the TS type specifically because a number of hardcoded/demo `ProjectSite` object literals exist elsewhere in `main.tsx` that predate the real backend cutover and don't set them. Any new field added to `ProjectSite` needs to be optional too, or those literals will fail to type-check (found this the hard way three times this session).
- **`ProjectSite.due` is a free-text display string** (`target_date_display` column -- literally named for display, not storage), not a real date. Values like `"TBD"` are normal (see `addDraftProject`). Never do `new Date(project.due)` and trust the result blindly -- see `parseProjectDueDate()` (main.tsx, right before `ProjectPortfolioHealth`) for the pattern: parse, check `Number.isNaN(parsed.getTime())`, and degrade to "no date" rather than showing a nonsense day count when it doesn't parse.
- Shared upload/signed-URL helpers (`uploadStorageObjectFile`, `getStorageObjectSignedUrl` in `persistence.ts`) are generic across buckets — new photo/file features should wrap these with a bucket-specific pair of thin functions (see `uploadShipmentPhotoFile` / `getShipmentPhotoDownloadUrl` for the pattern) rather than reimplementing upload logic.
- `.modal-panel-wide` (in `styles.css`) is the pattern for a modal that wraps a whole existing `<section className="panel ...">` (BOM table, Submittals list, etc.) instead of a small form — it neutralizes the inner section's own box styling (`.modal-panel-wide > .panel { border: none; box-shadow: none; padding: 0; }`) so it doesn't double-box. Pair with a `.modal-tile-close-row` for the close button when the wrapped content doesn't have its own `modal-header`.
- `ProjectTile` component (`main.tsx`) is the reusable stat-card-that-opens-a-modal building block established this session — reuse it for any future "collapse this section into an overview tile" work rather than hand-rolling another card pattern.
- **Offline photo queue** (`persistence.ts`: `queuePendingSitePhoto`/`flushPendingSitePhotos`, an IndexedDB-backed queue) already exists and is mature -- built specifically for "common in a parking garage" connectivity loss. `CameraCaptureModal.saveAll` (main.tsx ~13118) tries a normal upload first; on failure (offline or a real error, distinguished via `navigator.onLine` in the user-facing message) it queues the photo+blob in IndexedDB instead of losing it. A standing effect (main.tsx ~1245) flushes the queue on login/reload, on the browser's `online` event, and every 45s as a fallback (mobile browsers don't reliably fire `online`). Visible to the user via the "N photo(s) waiting to upload" pill next to the sync-status pill in the header. **Now covers Site Builder/Locations photos AND Shipping's packing photos** (`ownerType: "shipment"`, added 2026-08-19). The raw upload function (`handleUploadProjectShipmentPhoto`, and its Site Builder/Locations sibling `handleUploadProjectLocationImage`) is intentionally reused directly by `flushPendingSitePhotos` and never queues itself -- self-queueing there would duplicate a still-queued entry every time a retry fails again while offline. The queue-on-failure step lives one level up, in the function actually wired to the UI (`handleUploadProjectShipmentPhotoWithOfflineFallback` for Shipping; `CameraCaptureModal.saveAll` does the same job inline for Site Builder/Locations). Any *future* owner type needs the same split -- raw upload function stays queue-free, a thin wrapper at the UI call site does the queueing -- or it'll hit the same duplicate-on-retry bug.
- **Sync status pill** (`sync-status` div in the header, top-nav-actions) reflects exactly two things: whether the initial Supabase session/account-state load on page load succeeded, and whether a small `roleMode` preference blob saved back (`main.tsx` ~1156 and ~1202, two separate `useEffect`s). It is **not** a live tracker of every save across the app -- individual actions (inventory adjusts, project edits, etc.) report their own success/failure locally, not through this pill. If it's stuck on "Sync issue" (amber, hover for the real error), the reliable fix is reloading the page, which re-runs the session-load effect from scratch. Recolored "synced" from red to green 2026-08-18 (see work log) since the brand-red "ok" convention read as an alert here specifically.
- **Mobile bottom nav + install banner** (`main.tsx`: `MobileBottomNav`, `InstallAppBanner`, both defined right after `NavButton`) -- ported concept (not code) from the VLTD app's `BottomNav`/`PWAInstallBanner`. `MobileBottomNav` mirrors the top header's `allowedTabs` (not a hardcoded tab set) so it stays correct per role/per-user override: 2 tabs, a center action button, 1 tab, then "More" for whatever doesn't fit (plus Library/Admin). The center button is role-customizable via `ROLE_QUICK_ACTION` (a `Record<RoleMode, {view, label}>`) -- currently v1, a navigation shortcut with a role-specific label (e.g. sales sees "New Sale" but it just navigates to the Sales tab), not an auto-opened create form; E said this is fine for now and to upgrade specific roles to open a create modal directly when asked. Both components are rendered as siblings right after `</main>`, not nested inside it, so they don't inherit per-page layout quirks.

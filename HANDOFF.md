## Standing rules (always in force)
- Build things completely and correctly. Flag genuinely ambiguous requests instead of guessing — ask via AskUserQuestion before starting large/ambiguous features, not after.
- Fix small/quick issues immediately instead of deferring them.
- **Never leave a work-log entry as `(pending commit)` after the commit actually happens.** Confirmed 2026-08-25 as a standing requirement, after 36 entries had piled up needing a dedicated cleanup pass (E: "make a note to always keep the doc updated as we make changes, so that doesn't happen again" — this was real double-work E had to ask for once already). The work-log entry necessarily gets written *before* the code commit exists (it's part of the same commit, describing what that commit does), so it naturally goes in with a `(pending commit...)` placeholder -- the fix is a mandatory second step, same turn, not deferred: after the code commit succeeds, take the real short hash `git commit` prints, `Edit` HANDOFF.md's just-added entry to replace `(pending commit...)` with `` (`<hash>`, ...) ``, and push a small HANDOFF-only follow-up commit (exactly the pattern already used for "Mark migration NNN confirmed run" commits elsewhere in this doc -- never `git commit --amend`/force-push on something already pushed). Do this immediately after every commit, not batched into a later cleanup pass.
- **Mobile use is a core requirement, not a follow-up pass, for anything new or redesigned.** E (2026-08-22): "it should be a core function to make sure anything new or redesign keep mobile use in mind." Before calling any new feature or reworked page done, check it against the patterns below (don't wait for a dedicated "mobile rollout" batch to catch it later): wrap any new `<table>` in `.table-scroll` or give it `.stack-table-mobile` with `data-label`s (rule below), avoid fixed-width multi-column grids without a mobile 1fr override, avoid flex rows with unbounded text and no `min-width: 0`, and prefer reusing already-audited shared classes (`.compact-edit-section`, `.tag-picker-grid`, `.site-gallery-grid`, `.mobile-card-list`, etc.) over inventing new layout from scratch. See the "Mobile table -> card-list rollout" section below for the full list of what's already been checked and fixed.
- Before every commit/push: `npx tsc -b` (clean), `npx vite build` (clean), and check CSS brace balance if `styles.css` was touched.
- No local dev environment exists for the user — everything happens in this sandbox. Git push needs a credential helper pointed at the PAT stored in `.git-credentials-ergon` in the project root:
  `git config credential.helper "store --file='$(pwd)/.git-credentials-ergon'"` (must single-quote the path — it contains a space).
- **Any new migration that creates a table meant to be re-acquired/reused by key (locks, dedupe-by-key patterns, etc.) must use an atomic upsert-reclaim RPC, not a plain `INSERT`.** See "Transaction lock gotcha" below — this exact mistake caused every second-ever save on a given key to silently fail for an unknown length of time.
- Any function/handler that creates a new row a user will look back on later (inventory movements, audit-style records) should stamp who did it (`authSession.email`) at creation time. See `recordMovements()` in `Inventory` state for the established pattern — don't add a new inventory-movement-creating call site without routing it through that helper.
- **Any new "delete" action on something worth keeping a record of must soft-delete (`deleted_by_email`/`deleted_at` PATCH) and write a `deletion_log` row, never a plain DB `DELETE`.** Confirmed 2026-08-22 as a site-wide requirement (E: "Any deleted items are tracked and logged... Site Wide"), built as migration 088 across 15 entities. When adding a new deletable entity: give its table the same two columns, filter it out of normal loaders (`&deleted_at=is.null`, or the embedded-filter form for nested resources — see `PROJECT_LOCATIONS_DELETED_AT_FILTERS`/`SALES_QUOTE_DELETED_AT_FILTERS` in `persistence.ts`), and call `logDeletionEvent` from the delete/restore function itself so it can never be forgotten at the call site. If the entity stores a file in Storage, do **not** call `deleteStorageObject` on delete — leave the file in place so a restore isn't just an empty pointer (see `deleteProjectLocationImage`/`deleteSalesQuoteLocationImage`/`deletePurchaseOrderFile`). Restore UI is optional (add it if the entity is high-value enough to justify one) but the soft-delete + log is not. **Exception:** if the entity already has its own retire/archive flag as the deliberate "hide but keep for history" path (e.g. `equipment_types.is_retired`), Delete can stay a real hard delete instead of adding a second, redundant soft-delete layer — just still log it to `deletion_log`. See `deleteEquipmentType` (Device Recipes) for the reference implementation of this exception, including the friendly error when a FK with no `ON DELETE` clause blocks the delete.
- **Any raw `<table>` on a page reachable on mobile must be wrapped in a `.table-scroll` div** (`overflow-x: auto`). `html`/`body` now have `overflow-x: hidden` (2026-08-17 fix, see work log) specifically so a wide unwrapped table can't push the whole page wider than the viewport again — an unwrapped table doesn't just get its own horizontal scrollbar, it corrupts where `position: fixed` elements (the mobile bottom nav) render on that page. If you add a new data table, wrap it from the start.
- **When a feature ported from VLTD doesn't behave the same in Ergon, diff against VLTD's actual working config/code before inventing a theory.** Wasted a round-trip guessing "DevTools emulation is flaky" for the install banner not showing when the real answer (a manifest icon below Chrome's 192px minimum) was one `diff` against VLTD's `manifest.json` away. VLTD is right there on disk (`C:\Users\EK\VLTD`) -- check it first.
- **When E says "do the whole site"/"every page" and gives a standing go-ahead to keep working without checking in, do the whole thing — don't silently narrow it to a curated "high value" subset.** Converting only 3 "high-traffic" tables to mobile cards and quietly skipping ~18 admin/back-office ones (on the assumption they're desktop-only) cost E an hour: they came back expecting the full rollout done, found gaps, and had to spend time re-discovering and re-reporting what was missed instead of that hour being productive. If full bespoke treatment for every item is too slow to do in one pass, ship a lighter universal fallback for the rest in the same batch (see `.stack-table-mobile`) rather than leaving some silently undone — a complete-but-less-polished pass beats a polished-but-partial one when the user has explicitly asked for "everything" and stepped away.
- **Before declaring a CSS fix "sitewide" or "done," check whether another rule elsewhere in `styles.css` already targets the same class.** The `.metric-grid` mobile fix (tightened stat tiles, 2026-08-18) was correct in isolation but got silently overridden the whole time by a separate, pre-existing `@media (max-width: 760px)` block further down the file that also listed `.metric-grid` and forced it back to 1 column -- later rules win ties in the CSS cascade, and E had to point out the fix visibly wasn't working before this was caught. `grep -n "\.classname"` across the whole stylesheet before trusting a fix, not just the block you just wrote.
- **`.stack-table-mobile` hiding `<thead>` is only safe for self-descriptive text cells (names, emails, statuses).** A bare checkbox or a lone number means nothing once separated from its column header -- Notification Rules' channel-toggle checkboxes were completely ambiguous with the header gone (E: "wasted space... not tightening up and being readable"). Use the `data-label="<same text as the <th>>"` + `::before { content: attr(data-label) }` pattern (`styles.css`, in the `.stack-table-mobile` mobile block) on any `<td>` whose value needs the column context restored -- see Notification Rules, the Form Builder's Required checkbox, Project BOM, Site Hardware/Pre-Sales Rules, Standard Install Times, Schedule Template phases, and Catalog Price Change Requests for the pattern. When adding a new `stack-table-mobile` table, default to adding `data-label` on every non-obvious cell rather than assuming it'll be fine.
- **A Postgres column added as "a direct FK" in a comment is not actually a FK** unless the DDL has `references <table>(id)` on it. `inventory_movements.build_transaction_id` (migration 021) was silently a bare `uuid` for a long time because of exactly this — see migration 075. When adding a column meant to be embedded via PostgREST (`alias:table(cols)` select syntax), double-check the constraint actually exists, not just the comment claiming it does.
- **Row-action convention for any table/list, confirmed 2026-08-22:** long/wide rows never get an explicit "Edit" button — the row itself is the click target (`.clickable-row` on desktop `<tr>`/`<div>`, `role="button" tabIndex={0} onClick/onKeyDown` on a mobile card that also contains real interactive children, e.g. Inventory's card at `main.tsx` ~7638) that opens the edit view/modal. Any select/input/checkbox left directly on the row needs `onClick={(e) => e.stopPropagation()}` so it doesn't also fire the row's edit-open. **Delete/Remove is always a trash-can icon** (`<Trash2/>` in an `.icon-button`/`.icon-button compact-remove`), never button text -- E: "it very simple to me but some are this way and some aren't." Fixed sitewide in the same pass: Tasks (List rows, mobile cards, Board cards), Project BOM lines, and every standalone "Remove" button (PO paperwork, form builder fields, schedule template phases, pre-sales rules, site hardware rules, task hardware dependencies, purchase draft lines) -- see work log.
- **Tasks specifically: Delete lives only inside the Edit modal, not on the row/card at all** (`TaskEditorModal`'s footer, trash icon next to Close/Reopen Task) -- E: "On the task rows, Delete only lives in Edit." This only moved *where* the button is; Task deletion was already fully tracked before and after this change (soft delete stamping `deletedByEmail`/`deletedAt`, restorable from the Deleted Tasks panel, logged to the task activity log) -- see the site-wide deletion-tracking audit below before assuming any *other* entity has the same protection.
- **Any DELETE or PATCH that represents a single-record user action (delete, soft-delete, restore, retire, cancel, hold/resume, approve/reject, status change) must confirm a row was actually affected before treating it as a success.** `response.ok` is not enough -- PostgREST returns 200/204 for a write that an RLS policy silently blocked (0 rows changed) exactly the same as one that changed a real row. Add `Prefer: return=representation` to the request and check the returned array is non-empty before calling `logDeletionEvent` or updating local state; see `deleteEquipmentType` (persistence.ts) for the reference shape. Confirmed 2026-08-24 as a site-wide requirement (E: "we cant have local memory on these type of issues") after this exact gap made Delete Equipment Type silently no-op -- see the audit work-log entry for the full list of ~21 functions fixed in the same pass. Any *new* delete/status-change function must follow this pattern from the start, not get audited in later.
- **A failure needs a channel a logged-in user will actually see -- `setAuthStatus` is not one.** `authStatus` only renders on the signed-out login screen (`.auth-gate-status`) and, weakly, as a hover tooltip on the top-nav sync pill when paired with `setSyncStatus("error")`. Calling `setAuthStatus` alone from a handler that runs while logged in is a silent no-op to the user. Use `window.alert(error)` for one-off actions with no existing status surface, or an entity's own already-rendered local status state (e.g. `taskStatusMessage`, `inviteStatus`, `catalogStatus`) where one exists -- don't invent a new state variable without also rendering it somewhere.
- **Every new `api/*.js` serverless route must call `requireAuth(req, res)` (from `api/_lib/requireAuth.js`) as its first line, before touching `req.body`.** Confirmed 2026-08-27: all 7 existing routes (`send-invite-email`, `send-notification-email`, `send-notification-slack`, `send-proposal-email`, `send-submittal-email`, `send-push`, `sales-quote-extract`) were built and shipped with zero auth checks -- fully public POST endpoints on a public GitHub repo, discovered during a security review E asked for after a real incident on the VLTD sister project. Worst case found: `send-invite-email` let anyone on the internet send an email with an attacker-controlled link through this app's own trusted mailer, styled as a legitimate invite -- a phishing vector. The fix pattern (`requireAuth` verifies the caller's Supabase access token against `/auth/v1/user`, no new secrets needed) is now the required baseline for any route with no per-role logic; every client-side `fetch("/api/...")` call site must send `authorization: Bearer <accessToken>`. If a route ever needs stricter (e.g. admin-only) enforcement, add a role check on top of `requireAuth`, don't replace it. See the full work-log entry below for the complete list of what was checked and confirmed clean in the same pass (git history, `.env` handling, storage buckets, old RLS policies).

## Mobile table -> card-list rollout (in progress, 2026-08-18)
E: "the entire site should be optimized this way" (referring to the Product Catalog mobile card list) and gave a standing go-ahead to keep converting the rest of the wide desktop-style tables without checking in each time, as long as each one follows the same pattern -- just keep this doc updated per batch. **If you're picking this up mid-rollout, check the task list (TaskList tool) for the current in-progress/pending items**, then keep going with the pattern below.

**The pattern** (established on Product Catalog, `main.tsx` ~12251, and Site Builder, ~15242): below 760px, hide the existing `<table>` (wrapped in a `*-table-scroll` div, `display: none` in the same `@media (max-width: 760px)` block the table already had overrides in -- don't create a new duplicate media query, extend the existing one for that page) and show a parallel `.mobile-card-list` built from the *same* array/`.map()` the table uses, so there's no new data plumbing. Card building blocks are shared generic classes now (added 2026-08-18, `styles.css` ~5893): `.mobile-card-list` (container), `.mobile-card` (one card), `.mobile-card-row` (icon/title row), `.mobile-card-title`, `.mobile-card-meta` (small muted line), `.mobile-card-pills` (status badges), `.mobile-card-filters` (search/filter inputs pulled out of the table's `<thead>` filter row, since those were themselves only reachable via horizontal scroll -- always put filters at the top of the mobile list, not buried). Product Catalog and Site Builder predate the shared classes and use their own prefixed set (`.catalog-mobile-*`, `.site-builder-mobile-*`) -- don't bother retrofitting those, just use the shared classes for everything converted after Inventory.

**Nested-button gotcha:** if a row has real action buttons (Receive/Adjust, Delete, etc.), do NOT make the outer card a `<button>` -- HTML doesn't allow nesting interactive elements, and while React's direct-DOM rendering (not innerHTML parsing) means the browser mostly tolerates it, it's invalid markup and risky. Use `<div className="mobile-card" role="button" tabIndex={0} onClick={...} onKeyDown={(e) => (e.key === "Enter" || e.key === " ") && ...}>` instead, with real `<button>`s nested inside wrapped in a `<span onClick={(e) => e.stopPropagation()}>`. See Inventory's card (`main.tsx` ~7638) for the reference implementation. Site Builder's card (built one batch before this rule was written) does nest a delete `<button>` inside the outer `<button>` -- it works in practice but isn't the pattern to copy; worth fixing if touching that card again.

## Long-term roadmap: Ergon as the Slack/ClickUp/Drive replacement (agreed 2026-08-30, not started)

E's stated direction, from an overnight planning conversation (research → clarifying questions → design proposal → agreement, no code written for any of this yet): "we need 3 different apps and the info is spread out between Hubspot, Google Drive, ClickUp and Slack. I would like the ClickUp and Slack features with using google drive as a backup for items and not have to jump through all of these apps... eventually eliminate that app all together." HubSpot is explicitly deferred ("ignore for now" — eventual two-way sync for billing/project status is the only piece E wants from it, later). This is a multi-week initiative E already expects to take real time ("this may take weeks to build and test") — treat it as a standing roadmap to work through in phases, not a single feature request.

**The agreed design** (confirmed by E after the plan was played back):

- **Channels are one underlying concept**, surfaced in three places, not three separate systems:
  1. **Section channels** — one fixed, permanent "Discussion" tab per major app section (Sales, Purchasing, Marketing, Inventory, etc.), added to the existing sub-tab bar pattern already used in Inventory & Purchasing (Stock/Purchasing/Vendors + new Discussion tab); for single-view pages, becomes a 2-tab [Main | Discussion] layout. Singletons — always exist, never created/deleted by users.
  2. **Project channels** — every Project auto-gets one, tied to `project_id`. **Never dies.** Closing a project does not archive-and-lose its channel; the channel and its full history move with the project into wherever it lives afterward (the Client's ledger).
  3. **Client channels** — see the Clients section below. The client's own ongoing channel, plus a rolled-up view into every project channel that ever ran under that client.
  - All three share the same underlying table/shape (a channel optionally linked to a real entity, or to nobody for a real 1:1 DM — DMs already exist, migration 094).
  - **Auto-membership, not manual invites** — matches existing role/tab-access rules (whoever can already see a Project/section can see its channel) rather than a new per-channel membership system to administer.
  - The standalone Messages hub (exists today, DMs only) gets rebuilt into a real Slack-style sidebar: DMs, Projects, Sections grouped separately, each a view into the same underlying channel data the embedded tabs use.

- **Clients become a real entity — this is required, not optional, for the above to work.** Confirmed by checking the actual code: today's Client Ledger (`ClientLedger` component, main.tsx ~12922) is entirely per-*project* — `ledgerInfo`/`installedAssets` key off `project_id`, and `project.client` is just a repeated text field with zero deduplication. Two projects for the same real client ("Newport News Shipbuilding" appears on more than one project today) show as unrelated rows. To get E's actual ask ("when a project gets closed, that whole section goes under the Client as one large combined section") this needs:
  1. A real `clients` table.
  2. Existing `project.client` text values matched/linked to a real Client — auto-linked where unambiguous, but **needs a short manual reconciliation pass with E** for anything that doesn't match cleanly (e.g. is "Newport News" the same client as "Newport News Shipbuilding" and "Newport News 37th St.", or three different things?) — do not auto-guess this, it's exactly the kind of silent-wrong-merge that's expensive to untangle later. Show E the actual distinct client strings in the live data and let them confirm groupings in one pass before anything is merged.
  3. Client Ledger becomes a client-grouped view (one entry per Client, every project/site that ever ran for them rolled up underneath) instead of today's flat per-project list.
  4. The Client gets the same Discussion-tab pattern as everywhere else.

- **Search**: extend the existing global search (main.tsx ~5381, today: client-side substring match, 3 entity types only — inventory parts/POs/projects, shown as a dropdown) rather than replace it. Researched how Notion's is built/why it's well-regarded (their own writeups: workspaces under ~1,000 docs — Ergon's scale — skip vector/embedding search entirely and lean on ranking + UX):
  - Postgres full-text search (`tsvector`/`ts_rank`) across a much wider set of entities: add Tasks, Messages/channels (including closed/archived ones -- this is the actual fix for "old chats are hard to find," not the channel-merging above, which fixes *where things live* rather than *finding them regardless*), Vendors, Sales Quotes, Documents.

  - Keep the fast dropdown for quick jumps; add a real full-page results view (filterable by entity type, scopable to "just chats" vs "everything," per E's ask) for anything bigger than a few hits.
  - Rank by recency + exact-title-match boost as a first pass; usage-frequency boosting and an AI Q&A layer on top are legitimate later add-ons, not part of the initial build.

- **Google Drive**: auto-backup only (confirmed, not browse/import) — every file uploaded to Ergon (photos, documents, message attachments) also gets copied to a Drive folder automatically. Not a two-way sync, not a way to pull *existing* Drive files into Ergon.

## Data model / architecture notes
- Persistence: raw `fetch()` calls against Supabase REST in `src/persistence.ts` (no Supabase JS client) -- **still true as of Direct Messages (migration 094)**, which polls instead of using Postgres-changes realtime subscriptions specifically because there's no supabase-js/realtime client anywhere in this app. Adding one would be a bigger architectural change than anything else in that feature; flag it if E ever wants true realtime instead of the 5s/20s poll intervals.
- **The real "is this an actual logged-in app user" identity table is `app_known_users`** (migration 012: `user_id references auth.users(id)`, auto-upserted via `upsertKnownUser` on every login), not `team_members` (migration 019, explicitly NOT tied to auth.users -- someone can be a task-assignable "team member" without ever having logged in) and not the unused `profiles` table (migration 001, never populated -- see the much older mailer/purchase_orders notes on this). Any future feature needing "a real signed-in user" as a foreign key (Direct Messages, push subscriptions) should reference `app_known_users`/`auth.users`, not `team_members`.
- **`/api/send-push.js` is the first server route in this app using a Supabase *service-role* key** instead of a user's own access token -- every other API route either doesn't touch Supabase at all (email/Slack notification senders) or wasn't needed to look up data belonging to someone other than the calling user. `SUPABASE_SERVICE_ROLE_KEY` bypasses RLS entirely and must never get a `VITE_` prefix (which would expose it to client bundles) -- if a future feature needs the same "look something up for a user other than whoever's asking" shape, this is the reference implementation.
- Any new table needs `enable row level security` **plus** at least one policy, even if fully permissive (`using (true) with check (true)`) — otherwise triggers running as the calling user get blocked.
- Ref-number pattern to reuse for any future entity needing a stable sequential reference: create a `<entity>_ref_counters (year int primary key, next_seq int default 1)` table with RLS + policies, a `before insert` trigger doing `insert ... on conflict (year) do update set next_seq = next_seq + 1 returning next_seq - 1 into seq`, format as `'PREFIX-' || year || '-' || lpad(seq::text, 4, '0')`, and a backfill `do $$ ... $$` block for existing null rows.
- **Key-reuse table pattern** (locks, or anything else identified by a reusable key that gets "released"/soft-closed rather than deleted): never do a plain client-side `INSERT`. Write a `security definer` Postgres function that does `INSERT ... ON CONFLICT (key) DO UPDATE ... WHERE <row is actually free> RETURNING *`, call it via `rpc/<function_name>` from the client, and treat "no row returned" as "still locked." See migration 069 / `acquireTransactionLock` in `persistence.ts`.
- BOM lines (`BomLine` / `project_bom_lines`) have **no stable id** in the app layer — they're identified by `item` (product name) everywhere, including the new Shipping feature's line items (`item_name`, not a FK). Don't introduce a `bom_line_id` FK assuming one exists; it doesn't.
- `ProjectSite.locations` / `.shippingAddresses` / `.shipments` / `.saas*` fields are all **optional** (`?`) on the TS type specifically because a number of hardcoded/demo `ProjectSite` object literals exist elsewhere in `main.tsx` that predate the real backend cutover and don't set them. Values like `"TBD"` are normal (see `addDraftProject`). Never do `new Date(project.due)` and trust the result blindly -- see `parseProjectDueDate()` (main.tsx, right before `ProjectPortfolioHealth`) for the pattern: parse, check `Number.isNaN(parsed.getTime())`, and degrade to "no date" rather than showing a nonsense day count when it doesn't parse.

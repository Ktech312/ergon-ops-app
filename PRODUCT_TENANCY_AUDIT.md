# Ergon Productization Audit — Tenant Isolation & Configuration Baseline

Status: Read-only audit complete; no production code, database policy, migration, workflow, or business process was changed to produce this document
Created: 2026-09-08
Owner: Ergon leadership (decisions), engineering (implementation once decisions are made)
Scope authority: `PRODUCT_PLAN.md` (product direction), `PRODUCT_START_PLAN.md` (this is deliverable #2 in its "First deliverables" list — the "Productization and tenant-isolation gap audit")

## How to read this document

Three kinds of statement appear here, and they are kept visually distinct on purpose:

- **Confirmed current behavior** — read directly from the actual SQL migrations, server route code, or frontend source, with a file:line citation. Not inferred, not assumed. Every row's "Evidence" column is this kind of statement.
- **Inferred risk** — what the confirmed behavior would mean *if* a second company's data existed in the same database today. These are logical consequences of the confirmed behavior, not separately verified by creating a second company (no second company exists; none should be created before the work in this document's own §9 is complete).
- **Recommendation / proposed direction** — this document's own proposal for what to do about a finding. Nothing in a "Proposed Direction" or "Decision Needed" column has been approved, scheduled, or implemented. Per `PRODUCT_PLAN.md`'s process-protection rule, no existing business process is changed by this document; per `PRODUCT_START_PLAN.md`, no mechanical schema change (e.g. "add a workspace column everywhere") is authorized here either.

## Method

Three parallel, read-only research passes were run against the actual repository:

1. **Database**: every one of the 114 SQL migration files in `backend/supabase/migrations/` (`001_initial_ops_schema.sql` through `114_trusted_notification_creation.sql`), read in full — every `create table`, all 253 `create policy` statements, every `security definer` function, every storage bucket/policy.
2. **Server**: every file under `api/` (8 route files), `api/_lib/` (8 shared helpers), `api/cron/` (1 job), and `vercel.json`.
3. **Frontend**: `src/main.tsx` (25,213 lines) and `src/persistence.ts` (10,680 lines) — hard-coded identity/branding, global constant arrays, the Admin panel's actual configurable surface, search, notifications, localStorage, reporting/exports, and seed/demo data.

Every finding below is traceable to one of these three passes or to a direct follow-up read done to close a specific gap (noted where relevant). No file was edited during this audit.

## 2. Which database records have explicit company/workspace ownership, and which do not

**Confirmed current behavior: none.** All 86 tables in the schema were enumerated directly from their `create table` statements (see the database audit's full table for the complete list, file-by-file). Not one has a `company_id`, `workspace_id`, `tenant_id`, `org_id`, or semantically equivalent column. A repository-wide search for those four column-name patterns across every migration file returned zero matches.

| Area | Current Behavior | Evidence | Product Gap | Risk | Proposed Direction | Decision Needed |
|---|---|---|---|---|---|---|
| Every application table (all 86) | No table has any company/workspace/tenant column | Full table-by-file inventory produced during this audit (86 tables, `001` through `113`); zero `company_id`/`workspace_id`/`tenant_id`/`org_id` matches anywhere in `backend/supabase/migrations/` | No way to express "this row belongs to Company A" anywhere in the schema today | Critical — this is the foundational gap everything else in this document follows from | Add `workspace_id` incrementally, staged by table group, per §8/§9 — not mechanically to every table at once | Confirm the staged table-group order against the "shared records" list in `PRODUCT_PLAN.md` (see the cross-reference table below) |
| Closest-to-ownership concepts that exist but are **not** tenant boundaries | `departments` is an internal org-chart lookup table (e.g. "Warehouse," "Sales"), not a company boundary; `clients` is Ensight's own customer list (a CRM record, itself a candidate for workspace-scoping, not a scoping mechanism for other tables); `workspace_key` is a hard-coded legacy MVP-sync string (see §1) | `backend/supabase/migrations/001_initial_ops_schema.sql:11-18` (`departments`); `102_...sql:32` (`clients`); `022_...sql:5-9` (comment noting `projects.department_id`/`owner_id` were explicitly abandoned as a scoping mechanism in favor of plain columns) | None of these can be pressed into service as a stand-in for a real workspace column | Medium — a risk only if someone mistakenly treats one of these as "good enough" tenancy scoping later | Build the real `workspaces`/`workspace_id` model; do not repurpose `departments`, `clients`, or `workspace_key` for tenant isolation | — |

## 8. A safe proposed tenant/workspace architecture (Ergon becomes the first workspace)

This is a **proposal**, not an implementation plan authorized to proceed. It is deliberately staged (see §9) and preserves 100% of existing Ergon/Ensight data as the first, and initially only, workspace.

### Core new concepts

1. **`workspaces`** — one row per customer company. `id`, `name`, `slug`, `status` (active/suspended — no billing fields yet, per `PRODUCT_PLAN.md`'s explicit deferral of product-account billing), `created_at`.
2. **`workspace_members`** — replaces the *scoping* function of today's global `app_user_roles`/`app_admins`. Columns: `workspace_id`, `user_id`, `role_key` (reusing the existing `ROLE_KEY_OPTIONS` vocabulary — no need to redesign roles, just scope them), `is_workspace_admin boolean`. A single `auth.users` row can have membership rows in more than one workspace (see §10 — this needs an explicit decision, but the schema should support it either way since disallowing it later is easy and allowing it later is a bigger migration).
3. **`platform_admins`** — a small, separate table for Ergon's own platform-level staff (today's `app_admins`, or a curated subset of them — decision needed, §10). Platform admins are not automatically workspace admins of any customer's workspace.
4. **A "current workspace" resolution mechanism** — every request needs an answer to "which workspace is this for," used by every RLS policy and every server route. Candidate mechanisms (decision needed, §10):
   - A workspace id embedded in the user's JWT (`app_metadata`), refreshed on workspace switch — most robust, but requires an auth hook or a token-refresh step on switch.
   - A client-supplied header (`X-Workspace-Id`) validated server-side against `workspace_members` on every request — simpler to implement first, still fully safe if validated correctly, matches the existing pattern of routes already trusting nothing from the client without re-verifying it server-side.
5. **A `current_workspace_id()` (or equivalent) `security definer` SQL helper**, mirroring the existing `is_app_admin()`/`has_role()` pattern, used inside RLS policies the same way those functions already are.

### What changes, and what deliberately does not

- **Existing role-based RLS policies (Phase 9, `023`; catalog gate, `033`) are preserved, not replaced.** The workspace predicate is added *alongside* the existing role check (`using (workspace_id = current_workspace_id() and (is_app_admin(...) or has_role(...)))`), so the considerable existing work on "who within a company can do what" is not thrown away or redone.
- **`ROLE_KEY_OPTIONS`, `DEFAULT_TABS_BY_ROLE`, and the rest of §6's fixed vocabulary are not required to change for the first phase of tenancy work.** They become *per-workspace-selectable defaults* eventually (a later, separate product decision — see `PRODUCT_PLAN.md`'s own "Choose enabled modules and navigation" onboarding step), but nothing about tenant isolation itself requires touching them first.
- **The existing "shared records" already confirmed to exist (§2's cross-reference table)** — `clients`, `locations`/`project_locations`, `sales_quotes`/`sales_quote_proposals`, `product_catalog`/`equipment_types`, `projects`, `installed_assets`, `project_documents`, `tasks`, `conversations`/`channels` — are the concrete migration targets for adding `workspace_id`, in the staged order proposed in §9.
- **The records that don't exist yet** (Contact, Opportunity, Billing account, SaaS subscription, Support case) should be designed **with** `workspace_id` from their very first migration, avoiding a retrofit entirely for that half of the model.
- **Singleton/global tables** (`company_branding`, `notification_rules`, `standard_install_times`, `presales_hardware_rules`, `site_hardware_rules`) convert from a bare unique key to a `(workspace_id, key)` composite — same data, same admin UI, just workspace-scoped underneath.
- **Global-uniqueness constraints** (`vendors.name`, `locations.name`, `clients.name`, `team_members` email, `catalog_number`, `po_number`, `sku`, `quote_ref`) become `unique(workspace_id, x)`.
- **Reference-number counters** (`project_ref_counters`, `sales_quote_ref_counters`) get a composite PK `(workspace_id, year)`.
- **Storage** gets a workspace-scoped path-prefix convention (or per-workspace buckets — see §10) and rewritten bucket policies mirroring the existing `channel_id`-prefix pattern already used successfully for `message-attachments` (migrations 100/103/105 — this is proof the codebase already has a working example of path-prefix-based storage scoping to build the workspace version from).
- **External integrations** (email, Slack, push, AI extraction) get a `workspace_integration_settings`-style table; the current global env vars become the literal default values for the first (Ergon) workspace's row, so nothing breaks for Ergon itself on day one.

### Preserving existing Ergon data as the first workspace

The migration path for existing data is one `insert` and a set of `update ... set workspace_id = '<ergon-workspace-id>'` backfills, executed table-group by table-group (§9) — never a single mechanical "add the column everywhere" pass, per `PRODUCT_START_PLAN.md`'s explicit instruction. No existing row's other columns change. No existing user's role/access changes (their `app_user_roles` row becomes a `workspace_members` row in the one Ergon workspace, same role, same access).

## 10. Questions and decisions requiring owner discussion before implementation

1. **Can a user belong to more than one workspace** (e.g. a contractor working with two client companies)? This affects the `workspace_members` design and whether `team_members`' global email-uniqueness constraint should ever allow the same person to appear under two workspaces.
2. **What happens to today's `app_admins`** — do they become platform admins, workspace admins of the Ergon workspace, or both? `PRODUCT_PLAN.md` explicitly requires platform administration and company administration to "remain distinct concepts," but doesn't yet say how today's admins map onto that split.
3. **Should any of the currently-global-unique business names** (vendors, locations, clients, catalog numbers, PO numbers, SKUs, team-member emails) remain cross-workspace-unique for some legitimate reason (e.g. a vendor genuinely shared by two customer companies), or should all of them become strictly per-workspace?
4. **Exact "current workspace" resolution mechanism** — JWT claim vs. validated request header vs. something else (§8).
5. **Storage: one bucket per workspace, or shared buckets with a path-prefix convention?** The existing `message-attachments` channel-prefix pattern (migrations 100/103/105) is working proof the prefix approach is achievable in this codebase already.
6. **Should the fixed vertical-specific taxonomy** (catalog categories, site-hardware metrics) become fully admin-defined free-text, or should Ergon ship a "parking & traffic camera" starter template alongside a blank template for companies in a different vertical?
7. **Should the dead hard-coded seed-data array** in `main.tsx` (real client names/addresses, no longer used as a live fallback) be deleted now, as a small, isolated, zero-risk cleanup, independent of the larger tenancy timeline? Separately, should the still-*live* `emeraldQueenImportedProject` demo fallback be kept, removed, or replaced with a generic (non-Ensight-named) demo project?
8. **External integrations**: should Ergon offer a shared/default email/Slack/push/AI provider for smaller customers (with per-workspace override available), or should every workspace be required to bring its own credentials from day one?
9. **Reference-number scope**: is per-workspace numbering (every company's own `PRJ-2026-0001`) acceptable and expected, or must reference numbers be unique across all of Ergon's customers?
10. **Sequencing against the Sales-replacement work** described in `PRODUCT_START_PLAN.md` Steps 2-6: should that vertical-slice work proceed in parallel against the single existing (Ergon) workspace while tenancy Phases 1-4 are built underneath it, or should it wait? `PRODUCT_START_PLAN.md` principle #10 only says a *second company* must wait for verified isolation — it does not say whether new feature work on the *first* company must also wait.
11. **Two open verification items from §7** (does editing the Proposal Template or a Schedule Template retroactively affect already-signed quotes / already-scheduled projects?) should be answered with a direct, targeted code read before any versioning work is scoped — this audit intentionally did not guess at behavior it did not verify.
12. **Should the two authorization-hardening precedents already in this codebase** — the Catalog Price Change Requests propose/review/approve workflow (§7), and the security-review-driven closures already recorded in `HANDOFF.md` for the notifications/rate-limiting work — be treated as the house style to extend into the workspace-admin and billing-review approval flows `PRODUCT_PLAN.md` calls for, or should those get their own design pass?

## Summary

Every one of the ten requested areas was audited against the real, current codebase — 114 migrations read in full, all 8 server routes and 8 shared helpers, and the two main frontend files (36,000 combined lines) — with file:line citations throughout, not inferred from feature names. The headline finding, confirmed independently by all three research passes: **zero tables in this schema have any company/workspace/tenant column, the two authorization primitives (`app_admins`, `app_user_roles`) are both global with no company dimension, and the dominant RLS pattern across most business tables is still fully open to any signed-in user** — a deliberate and well-reasoned design for a single-company internal tool, but one that would mix or expose data across companies immediately if a second company were added to this database without the staged work proposed in §§8-9.

Nothing in this document has been implemented. §9's staged approach and §10's open questions are the recommended next step: owner discussion and decisions, before any schema or code change begins.
